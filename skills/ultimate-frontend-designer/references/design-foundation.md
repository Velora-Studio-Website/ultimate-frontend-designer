# 设计系统、字体与 Logo

对应 `design_system` 与 `brand_assets` 两个阶段。目标是先用图片模型得到可读的视觉结果，再把它固化成可实现的规范。

## 从用户问题到设计方向

在 brief 内完成以下推理，复用用户已给的信息，不另建一套需求问卷：

1. Empathize：谁在什么场景下使用页面，要完成什么，目前卡在哪里，有什么替代办法？信息标为用户提供、实际观察、有来源资料或假设。没有证据不虚构人口特征、访谈和行为。
2. Define：用“用户需要完成 X，因为 Y 阻碍”明确问题；选一个最有价值的“如何帮助用户……”问题，避免把“做得高级”当用户需求。
3. Ideate：有重大开放问题时比较少量不同方向，通常二至三个即可；从用户价值、实现可行性、素材成本与维护成本说明取舍。用户已锁定方向时只探索仍开放的部分，不重选品牌。
4. Prototype：选出最危险的假设，先用关键界面的图片稿或故事板检查。例如首屏能否说明产品、比较界面能否帮助选型。此步骤仍属于图片设计，不能用正式产品页面代替 Design Gate；通过后补齐约定的完整页面稿。
5. Test：预先写下任务、观察方法与成功/失败条件。真实用户测试只有实际参与和记录才算执行；模型自检可检验信息完整性，不能证明用户需求、理解率或转化率。反馈失败时修改对应假设或设计，不重启全项目。

每个关键决定在 brief 中用一条短记录串起来：用户任务 → 证据或假设 → 设计选择及理由 → 对应页面/素材 → 验证方法及结果。不要为每个圆角生成记录，也不要凭空填转化目标；定量阈值来自约定，缺少基线就用明确的任务完成条件。

按页面用途选择表达强度：persuade 优先价值与行动，operate 优先任务效率与状态，read 优先理解与阅读，experience 优先作品本身。同一项目可混用用途，但品牌语言保持一致。图片先行指设计方法，不要求每个后台和文档区块都塞装饰图。

## 有依据的视觉表达

从产品的材料、使用环境、语言和内容中提炼 Concept Spine，而非只用行业关键词挑模板。明确颜色、字形、构图、图片处理与一个适合的记忆点；记忆点可以是清晰的比较方式或精确的信息组织，不强制华丽效果。

提交生成前做替换检查：换成完全不同的品牌后，这套理由若仍然一字不差地成立，就补充本项目依据。克制或常见布局可以是正确选择，不为了“反模板”否定用户指定风格。编号只表示真实顺序，图表只表达真实数据，空白服务分组和阅读。

ui-ux-pro-max 可按一个问题检索，如字体语言覆盖、错误反馈、表单结构；验证结果与实际产品/平台匹配后才采纳。Better Design MCP 可按需读取相关原则，但不默认安装 catalog、改品牌或创建远程设计系统。二者都提供建议，不代替本项目的视觉板。

## 颜色、字体与组件的可实现规则

保留现有 tokens 与颜色格式；新体系按背景、表面、正文、次级文字、边框、交互与状态定义语义 token。组件引用语义角色，不因颜色相同就拿分隔线 token 当文字色。只创建实际使用的色阶和状态，颜色之外提供标签或图标反馈。

区分品牌色、行动强调和状态色。一个视图中的同级行动有清楚的主次，不因每个区块都想突出而全用主按钮。实测文字与真实背景的组合；透明叠层和背景图需包含在检查中。报告实际算出的值、使用的规则阈值和测量条件，图片模型的视觉判断不能代替计算。只检验约定主题，不擅自扩展暗色模式。

标题、正文、标签与数据各有明确角色，依据真实内容检查字重、行长、换行与中英混排，不强制所有项目使用同一字体或字号。视觉板中的字形仅为方向，实际字体覆盖与加载后布局需要在浏览器核对。

细节检查包括嵌套圆角与内边距协调、图标的光学校准、同一套图标的笔画一致性、边框表达结构、阴影表达层级。具体数值服从当前设计系统；不把专家配方里的缩放、模糊或弹簧参数变成全站强制值。non-animate 仍按静态反馈约定执行。

## 设计系统视觉板

正式制作网页前，调用图片模型生成设计系统视觉板，至少覆盖整体视觉、组件和 UX／页面结构。内容多时拆成多张板，不要把所有信息压进一张读不清的巨图。

| 范围 | 必须明确的设计结果 |
| --- | --- |
| 视觉方向 | 概念主线、构图、画面密度、留白、图像处理与层级 |
| 色彩 | 背景、表面、文字、边框、强调色和必要的语义状态色 |
| 排版基础 | 标题、正文、标签、按钮、数字的比例、字重、行距与字距 |
| 布局 | 容器、栅格、间距、对齐、区块节奏和初步响应式原则 |
| UI | 本项目真正需要的导航、按钮、卡片、表单及其他组件 |
| 状态 | 适用的 hover、focus、active、disabled、loading、error、empty、success |
| UX | 信息架构、主要任务路径、反馈、异常处理和 CTA 层级 |
| 素材语言 | 照片、插画、图标、产品图、背景、纹理、圆角、边框与阴影规则 |
| Guidelines | 复用规则、命名变体、允许变化与禁止误用 |

组件按业务需要选择，不为凑完整度添加无关模块，也不要把所有区块机械地做成同一种卡片网格。不要每个项目都套黑底、渐变、玻璃卡片和悬浮物；把视觉方向写成具体决定，例如图片尺度、排版对比、构图、留白、材质、配色和区块节奏。

营销页围绕信息理解与行动组织，电商页围绕商品信息与购买路径组织，功能型 Web App 围绕核心任务、状态与效率组织；不要为了视觉效果遮挡关键操作。

查看生成结果后整理成 `design-system.md` 与 `tokens.json`。tokens 覆盖适用的颜色值、排版、间距、圆角、边框、阴影、布局与断点，动效规则等 motion_mode 确定后补齐。核对图中的文字、标签与数值，不要把图片模型可能写错的标注直接当成规范；视觉板与结构化规范冲突时先修订，始终只保留一个当前有效版本。

退出条件：适用范围都有真实视觉结果和可实现规则；视觉板可读且已亲自查看；与 `design-system.md`、`tokens.json` 一致。

## 字体

用图片模型生成排版方向，展示真实的标题、正文、导航、按钮、标签与数字。中文项目要包含中文、英文、中英混排和标点样例。

让图片模型提出字形气质、粗细、宽窄、节奏与搭配方向，再映射到真实可用、许可明确、语言覆盖合适的网页字体，记录 fallback 与加载策略。许可或来源无法核验时标 pending，不要写进 tokens 当作已定方案。

字形图片不是可安装字体。网页正文、价格、按钮和标签使用真实文字，不用图片代替。不向用户分发运行环境中的字体文件。

## Logo

已有字体和 Logo 默认保留，只有在用户授权品牌改版时才替换。没有品牌名称时先取得名称，或使用用户允许的工作名称并标为临时提案。

需要新标识时，由图片模型生成与设计系统一致的方向，并准备实际需要的主标识、字标或组合标识、单色与深浅背景版本、favicon，以及留白和小尺寸使用规则。

Logo 展示板不等于可用素材。透明背景、矢量和文件格式必须实际打开检查；把位图封装进 SVG 不算矢量文件。

退出条件：字体视觉已落实为可用方案；既有品牌被正确保留或新标识素材真实可用；字体与 Logo 规则已回填设计系统。自检通过不等于用户批准。
