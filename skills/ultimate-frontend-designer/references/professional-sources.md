# 专业来源：标准、启发式与项目证据的边界

本册提供查证入口与使用方法，不替代标准全文、真实研究或项目验收。
核对日期：2026-10-26；外链可能更新，交付时保留所用版本与适用条款。
本册的原创示例均为教学模拟；来源概括从简，不转载原文或整套案例。
关联方法：[内容证据](content-evidence.md)、[行业内容](industry-content.md)、[专业工艺](professional-craft.md)。

## 1. 先区分来源能够证明什么

标准给出要求；组件指南给出实现模式；启发式帮助发现问题；产品事实另需证据。
来源权威不等于适用：WCAG 不能证明营销承诺，性能指标不能证明购买流程正确。
记录来源标题、URL、版本或更新日、访问日、定位条款和应用对象。
无法读取全文时标明范围，不能把搜索摘要升级为全文已核对。
摘要只记录本次需要的原则；派生设计建议注明是项目判断，不伪装成原文规定。
引用许可与事实核验分别检查，能核实内容不等于能复制其图片与案例。
失败反例：在页尾放一个 W3C 链接，便把所有交互标为“符合 WCAG”。
验证：每个引用都能回答“支撑哪一句、适用于什么、还缺什么测试”。

## 2. W3C WCAG 2.2：可测要求与等级

入口：[WCAG 2.2](https://www.w3.org/TR/WCAG22/)。
核对版本：页面列示 2024-12-12 W3C Recommendation；发布前复查勘误。
简要概括：要求按成功准则和等级判断；局部测试不足以宣布完整符合。
1.4.3（AA）：普通文字对比度至少 4.5:1，大号文字至少 3:1；有特定例外。
大号通常为至少 18 pt 或 14 pt 粗体，CJK 使用等效字号；不是任意视觉大标题。
按 96 CSS px/in 换算约 24 px、18.67 px；字重与等效定义需核查。
1.4.11（AA）：必要组件与图形视觉信息通常至少 3:1，需核查适用对象及例外。
1.4.4（AA）：文字可放大至 200% 而不丢内容或功能；字幕及图像文字有例外。
1.4.10（AA）：纵向内容在等效 320 CSS px 宽重排；必要二维部分有例外。
2.5.8（AA）：目标至少 24×24 CSS px，存在间距、等效、行内、代理控制、必要例外。
间距例外按各小目标中心的直径 24 CSS px 圆与其他目标或圆不相交判断。
2.5.5 的 44×44 CSS px 属 AAA，并有例外，不能混称 AA。
2.4.7（AA）要求可见焦点；2.4.11（AA）要求焦点组件不被作者内容完全遮住。
2.4.13 的焦点外观要求属 AAA；不可把其细节当作所有 AA 焦点的统一阈值。
以上为精选条款速查；完整适用条件、定义与符合性要求必须回到标准。

应用方法：建立“页面—状态—准则—测试步骤—结果”映射，逐项保留证据。
原创示例：预约确认按钮被底部宣传条完全遮住，记录焦点状态并检查相关条款。
对比度测试要使用最终合成背景；组件截图只能支持对应状态的结论。
失败反例：自动扫描零错误，就向客户写“全站 WCAG 2.2 AA 合规”。
修复：补人工任务检查，限定结论到实际页面与准则，列出未覆盖部分。
验证：能复现测量与任务；是否达到完整符合性另按标准范围评估。

## 3. APG：组件语义与键盘行为参考

入口：[ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/)。
简要概括：以常见组件模式说明角色、状态、名称与键盘支持，并提供实现示例。
它是实现指导，不能作为复制组件后自动取得 WCAG 符合性的凭证。
适用条件：确实需要自定义对话框、标签页或组合框，原生元素不能直接满足任务。
方法：先选匹配模式，再核对其键盘约定、名称、状态、焦点及实际 DOM。
不要将视觉相似当模式相同；导航链接组不必因横向排列就变成 tabs。
原创示例：订单筛选用原生 select 即可完成，不额外重造复杂组合框。
需要搜索选择时再评估组合框，并测试输入、候选读取、选择和取消。
失败反例：给 div 加 role="button" 就认为键盘和状态反馈已自动实现。
修复：优先原生按钮；自定义时明确实现行为，并用实际任务验证。
验证：记录浏览器与辅助技术组合，测试进入、操作、退出和返回后的焦点。
指南示例不是所有环境都已适配的成品，项目仍需自己的兼容性证据。

## 4. NNG：启发式用于找问题，不用于证明指标

入口：[10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)。
页面核对信息：最初发表于 1994-04-24，页面标记复审日期 2024-01-30。
简要概括：用状态可见、贴合现实、用户控制、预防错误等通用原则辅助评审。
这些是启发式，不是本项目用户研究结果，也不是定量转化效果保证。
适用条件：在原型或实现评审中快速发现容易解释和复现的交互问题。
方法：每个发现写具体位置、任务、观察、后果和修复建议，避免只写原则名称。
原创示例：提交报价需求后无反馈，用户再次点击，可能产生重复请求。
建议：展示处理中和明确结果，并按真实服务能力处理重复提交。
失败反例：“满足十条，所以用户满意度必然提高 30%。”
修复：删除无依据数字；用任务观察或适当的后续研究检验结果。
验证：另一位评审者可重现问题；修复后同一任务得到明确反馈。
无法找到问题不代表没有问题，启发式审查不替代目标用户完成任务的证据。

## 5. Carbon Content：把界面文字当作产品的一部分

入口：[Carbon Content](https://www.carbondesignsystem.com/building-blocks/foundations/content)。
页面核对信息：标记更新日期 2026-09-30；已通过正文提取核对内容基础部分。
简要概括：强调清晰、有目的且一致的界面文字，并连接术语、数字与可访问性写作资源。
它服务于 IBM/Carbon 体系；其中语言惯例不能不经判断原样套用中文产品。
适用条件：多位写作者维护同一产品，术语、提示和数量表达开始漂移。
方法：维护小型术语表，记录对象名、动作名、禁用同义词及上下文。
原创示例：导航叫“工作区”，邀请提示也叫“工作区”，不突然改称“团队空间”。
错误消息写清问题、受影响输入及可行下一步，但不泄漏敏感服务信息。
失败反例：“Oops，系统开小差啦”，没有说明保存是否成功，也没有恢复入口。
修复：按真实状态写“保存失败，输入仍保留。请重试。”仅在确有保留时采用。
验证：跨导航、表单、消息、帮助与导出检查术语，并观察用户能否理解下一步。
不在此声称已逐页核对所有下游 IBM 资源；具体规则需要时再核原文。

## 6. Web Vitals：体验指标的口径与局限

入口：[Web Vitals](https://web.dev/articles/vitals)。
页面核对信息：发表于 2020-05-04，标记更新日期 2024-10-31。
简要概括：核心指标分别覆盖加载、交互响应与视觉稳定性，需结合真实用户数据。
推荐良好值：LCP ≤2.5 s、INP ≤200 ms、CLS ≤0.1。
判断口径为第 75 百分位，分别看移动端与桌面端，三项均达推荐值。
适用条件：评估真实加载和操作体验，并定位影响用户任务的性能瓶颈。
方法：实验室数据用于定位，现场数据用于观察实际用户分布；明确样本与时间窗。
原创示例：筛选触发长计算，界面迟迟不反馈；先测交互轨迹，再拆分或优化计算。
预留图片空间可改善布局稳定，但是否改善需复测，不能预填提升百分比。
失败反例：一次本机 Lighthouse 高分就宣布真实用户 INP 已达到良好。
修复：区分工具支持的指标和测量环境，尚无现场数据就如实记录 UNKNOWN。
验证：保留 URL、版本、设备、网络、测量时间与数据来源，比较同等条件。
这些指标不覆盖内容真实性、权限正确性或所有可用性问题，需要独立验收。

## 7. 来源进入 Gate 的操作顺序

研究阶段：把原文要求与本项目判断拆开，每条高影响断言挂来源和条件。
brief 阶段：确定要解决的用户问题，记录已确认事实、假设与待补资料。
覆盖表阶段：将用户问题连到页面内容、状态、证据及可观察动作。
DesignGate：核查设计是否表达已确认条件，不能把未来测试写成已通过。
BuildGate：对实际构建产物执行检查，结果只覆盖被测试的对象与状态。
发布前：重核动态业务资料及变化过的规范，授权仍按项目约定执行。
失败反例：更新规范链接后沿用旧检查结论，却没有检查条款和产品是否变化。
修复：按变更影响重验对应条目，其余证据保留原时间与范围。
验收报告分别标 PASS、FAIL、UNAVAILABLE、UNKNOWN，不把缺证写成通过。
来源分册写完只代表参考资料已整理，不代表任一产品通过可用性、性能或合规验收。
